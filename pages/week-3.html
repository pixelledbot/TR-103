DAILY TRAINING RECORD

Learning Journal

The third week focused on DevOps tools used to manage source code and automate software workflows. Git and GitHub were introduced for version control and collaboration, followed by CI/CD concepts and an introduction to Jenkins pipelines.

01 DAY ONE

VERSION CONTROL

Introduction to Git and Version Control

The first session introduced version control and its importance in software development. Version control systems maintain a history of changes made to project files, making it easier to track modifications and work with different versions of a project.

Git was introduced as a distributed version control system. It allows developers to maintain repositories locally, create commits and collaborate with other developers.

CONCEPTS COVERED
  • Version control systems
  • Introduction to Git
  • Repositories
  • Commits and project history
  • Distributed version control
KEY LEARNING

Understood how Git tracks changes and helps developers maintain organised project histories.

Daily Reflection

This session introduced an essential DevOps tool and explained why tracking source-code changes is important during software development.

02 DAY TWO

GIT PRACTICAL

Git Repository and Basic Commands

This session covered creating and managing Git repositories. A repository stores the project files and their version history. Git commands were used to initialise a repository, inspect changes and save project versions.

Initialising a Repository

git --version
git config --global user.name "Your Name"
git config --global user.email "you@example.com"

mkdir my-project
cd my-project

git init
git status

Tracking Project Files

git add filename
git add .
git commit -m "Initial project commit"

The staging area allows selected changes to be prepared before creating a commit. A commit records a snapshot of the staged changes in the repository history.

COMMANDS PRACTISED
  • git init
  • git status
  • git add
  • git commit
  • git log
KEY LEARNING

Learned how to initialise a Git repository, stage files and save changes through commits.

Daily Reflection

Practising Git commands helped clarify the workflow of tracking, staging and recording project changes.

03 DAY THREE

GITHUB WORKFLOW

GitHub Repositories and Collaboration

The third session introduced GitHub as a web-based platform for hosting Git repositories and supporting collaborative software development.

The workflow of creating a GitHub repository and connecting it with a local repository was explored. Common operations such as cloning, pushing and pulling changes were covered.

Common GitHub Workflow Commands

# Clone an existing repository
git clone https://github.com/username/repository.git

# Check repository status
git status

# Stage and commit changes
git add .
git commit -m "Update project files"

# Connect a local repository to GitHub
git remote add origin https://github.com/username/repository.git

# Push changes to GitHub
git push -u origin main

# Retrieve remote changes
git pull origin main

The session also introduced pull requests. A pull request allows proposed changes to be reviewed before they are merged into another branch.

TOPICS COVERED
  • GitHub repository creation
  • Cloning repositories
  • Push and pull operations
  • Remote repositories
  • Pull requests
KEY LEARNING

Understood how local Git repositories connect to GitHub and how developers share and review code changes.

Daily Reflection

This session connected local version control with online collaboration and demonstrated how GitHub supports team-based development.

04 DAY FOUR

AUTOMATION CONCEPTS

Introduction to CI/CD and Jenkins

This session introduced Continuous Integration and Continuous Delivery or Deployment (CI/CD). These practices help automate parts of the software development process.

Continuous Integration involves frequently integrating code changes into a shared repository and validating them through automated builds and tests.

Continuous Delivery focuses on preparing validated software for release, while Continuous Deployment can automatically release successful changes to production.

Introduction to Jenkins

Jenkins was introduced as an automation server used to create and execute CI/CD pipelines. It can connect with source-code repositories and run automated tasks whenever changes are detected.

CI/CD CONCEPTS
  • Continuous Integration
  • Continuous Delivery
  • Continuous Deployment
  • Automated builds
  • Automated testing
JENKINS CONCEPTS
  • Jenkins server
  • Jobs and pipelines
  • Build automation
  • Pipeline stages
Daily Reflection

Learned how CI/CD reduces repetitive manual steps and how Jenkins can coordinate automated software workflows.

05 DAY FIVE

JENKINS PRACTICAL

Setting Up a Jenkins Pipeline and Automating Builds

The final session focused on the basic setup of a Jenkins pipeline and its role in automating the build process.

A pipeline represents a sequence of automated stages that perform tasks such as checking out source code, building an application and running tests.

Example Jenkins Pipeline

A Jenkins pipeline can be defined in a file named Jenkinsfile. The following example demonstrates a simple pipeline structure: 

pipeline {
    agent any

    stages {

        stage('Build') {
            steps {
                echo 'Building the application'
            }
        }

        stage('Test') {
            steps {
                echo 'Running application tests'
            }
        }

        stage('Complete') {
            steps {
                echo 'Pipeline completed'
            }
        }
    }
}

Basic Pipeline Workflow

  1. Create or select a source-code repository.
  2. Configure a Jenkins job or pipeline.
  3. Connect the project repository.
  4. Define the required pipeline stages.
  5. Execute the pipeline.
  6. Review the build output and status.

The build process can be triggered manually or configured to run automatically when new code changes are pushed to the repository.

Daily Reflection

The practical session demonstrated how Jenkins pipelines organise automated tasks and provide visibility into the build process.
